Controle de Versão

Controle de versão é uma prática fundamental no desenvolvimento de software. Ele permite registrar, organizar e acompanhar todas as mudanças feitas em um projeto ao longo do tempo. Com ele, é possível saber quem alterou um arquivo, quando a alteração foi feita, o que foi modificado e por qual motivo.

Em projetos profissionais, o controle de versão é indispensável. Ele ajuda desenvolvedores a trabalharem em equipe, evita perda de código, facilita a correção de erros e permite manter um histórico completo da evolução do sistema.

O que é controle de versão?

Controle de versão é um sistema usado para gerenciar alterações em arquivos. No contexto da programação, ele é usado principalmente para controlar mudanças no código-fonte de um projeto.

Sem controle de versão, é comum que os arquivos fiquem desorganizados, com nomes como:

projeto_final.zip projeto_final_corrigido.zip projeto_final_agora_vai.zip projeto_final_definitivo_2.zip

Esse tipo de organização é perigoso, porque torna difícil saber qual versão está correta, quais mudanças foram feitas e como voltar para uma versão anterior caso algo dê errado.

Com controle de versão, o projeto passa a ter um histórico organizado. Cada alteração importante pode ser registrada com uma mensagem explicando o que foi feito.

Para que serve?

O controle de versão serve para manter o projeto seguro, organizado e rastreável. Ele permite que o desenvolvedor trabalhe com mais confiança, porque qualquer alteração pode ser analisada, comparada ou revertida.

Registrar mudanças Voltar versões antigas Trabalhar em equipe Evitar perda de código Criar novas funcionalidades Corrigir erros com segurança Organizar o histórico Publicar projetos

Por que isso é importante?

Durante o desenvolvimento de um sistema, o código muda o tempo todo. Novas funcionalidades são criadas, bugs são corrigidos, arquivos são reorganizados e melhorias são feitas constantemente.

Se essas mudanças não forem controladas, o projeto pode virar uma bagunça. Um erro simples pode quebrar uma funcionalidade importante, e sem histórico fica difícil descobrir onde o problema começou.

O controle de versão resolve esse problema porque registra cada etapa do desenvolvimento. Assim, o time consegue acompanhar a evolução do projeto e tomar decisões com base no histórico real do código.

Git e GitHub são a mesma coisa?

Não. Git e GitHub estão relacionados, mas não são a mesma coisa.

Git

Git é o sistema de controle de versão. Ele funciona no computador do desenvolvedor e é responsável por registrar o histórico do projeto, criar commits, branches, merges e controlar as mudanças nos arquivos.

GitHub

GitHub é uma plataforma online onde os repositórios Git podem ser armazenados. Ele permite hospedar código, colaborar com outras pessoas, abrir pull requests, registrar issues e publicar projetos.

Git: ferramenta local GitHub: plataforma online Git controla versões GitHub hospeda repositórios

Conceitos principais

Repositório

Um repositório é o local onde o projeto é armazenado junto com todo o seu histórico de alterações. Ele pode existir localmente no computador ou remotamente em plataformas como GitHub.

Commit

Um commit é como um ponto salvo na história do projeto. Ele registra uma alteração ou um conjunto de alterações feitas nos arquivos.

Cada commit deve ter uma mensagem clara explicando o que foi feito. Uma boa mensagem ajuda outros desenvolvedores a entenderem a evolução do projeto.

Branch

Uma branch é uma linha separada de desenvolvimento. Ela permite criar ou testar funcionalidades sem alterar diretamente a versão principal do projeto.

Merge

Merge é o processo de juntar o conteúdo de uma branch com outra. Normalmente, uma funcionalidade é criada em uma branch separada e depois unida à branch principal.

Remote

Remote é o repositório remoto, ou seja, a versão do projeto armazenada online. O GitHub é um exemplo de local onde um repositório remoto pode ficar hospedado.

Estados dos arquivos no Git

O Git trabalha com alguns estados principais para os arquivos. Entender esses estados ajuda muito a usar a ferramenta corretamente.

Working Directory

É a área onde você está trabalhando. Quando você edita um arquivo no VS Code, por exemplo, a alteração acontece primeiro no diretório de trabalho.

Staging Area

É a área de preparação. Antes de criar um commit, você escolhe quais alterações farão parte dele. Essa escolha é feita com o comando git add.

Repository

É onde o histórico confirmado fica salvo. Quando você executa um commit, as alterações preparadas são registradas no repositório.

Modificado Preparado Commitado Enviado ao remoto

Fluxo básico de uso

Um fluxo comum de trabalho com Git segue algumas etapas simples. Primeiro, o desenvolvedor altera os arquivos. Depois, verifica o estado do projeto, adiciona as mudanças, cria um commit e envia para o repositório remoto.

1. Verificar o estado do projeto

git status

Esse comando mostra quais arquivos foram modificados, quais estão preparados para commit e se existem alterações pendentes.

2. Adicionar arquivos para o commit

git add .

Esse comando adiciona todas as alterações para a área de preparação.

3. Criar um commit

git commit -m "Mensagem explicando a alteração"

Esse comando registra oficialmente as alterações no histórico do projeto.

4. Enviar para o GitHub

git push

Esse comando envia os commits locais para o repositório remoto.

Como iniciar um projeto com Git

Para começar a usar Git em um projeto, primeiro é necessário iniciar um repositório dentro da pasta do projeto. 

git init

Depois disso, o Git começa a controlar as alterações feitas naquela pasta.

Em seguida, é comum adicionar os arquivos e criar o primeiro commit. 

git add .
git commit -m "Primeiro commit"

Caso o projeto também tenha um repositório no GitHub, é possível conectar o projeto local ao repositório remoto. 

git remote add origin URL_DO_REPOSITORIO
git push -u origin main

Como clonar um projeto

Clonar um projeto significa copiar um repositório remoto para o computador local. Isso é comum quando você quer trabalhar em um projeto que já existe no GitHub. 

git clone URL_DO_REPOSITORIO

Depois de clonar, uma nova pasta será criada com todos os arquivos do projeto e o histórico do Git.

Branches na prática

Branches são muito usadas para desenvolver funcionalidades sem mexer diretamente na versão principal do projeto. Isso evita que o código principal fique instável.

Criar uma branch

git switch -c nome-da-branch

Trocar de branch

git switch nome-da-branch

Listar branches

git branch

Voltar para a branch principal

git switch main

Um bom hábito é criar uma branch para cada funcionalidade ou correção importante.

login-usuario corrige-menu pagina-comentarios melhora-layout

Merge

Merge é usado para juntar o conteúdo de uma branch em outra. Por exemplo, depois de terminar uma funcionalidade em uma branch separada, você pode unir essa branch à branch principal. 

git switch main
git pull
git merge nome-da-branch
git push

Esse fluxo atualiza a branch principal, junta as mudanças da outra branch e envia o resultado para o GitHub.

Conflitos de merge

Um conflito acontece quando o Git não consegue decidir automaticamente qual alteração deve ser mantida. Isso geralmente ocorre quando duas pessoas alteram a mesma parte de um arquivo.

Quando há conflito, o Git marca o trecho problemático dentro do arquivo. O desenvolvedor precisa abrir o arquivo, escolher qual versão manter, salvar e depois finalizar o merge.

Conflitos não significam que o projeto está perdido. Eles são normais em trabalhos em equipe e fazem parte do processo profissional de desenvolvimento.

Pull e Push

Push

Push envia os commits do seu computador para o repositório remoto. 

git push

Pull

Pull baixa as alterações mais recentes do repositório remoto para o seu computador. 

git pull

Antes de começar a trabalhar em um projeto em equipe, é uma boa prática executar git pull para garantir que você está usando a versão mais atualizada do código.

Boas práticas

Usar Git não é apenas decorar comandos. Também é importante seguir boas práticas para manter o projeto organizado e profissional.

Fazer commits pequenos Escrever mensagens claras Criar branches por tarefa Não enviar arquivos sensíveis Atualizar antes de alterar Revisar antes de commitar Usar .gitignore Evitar commits enormes

Exemplo de mensagem ruim

git commit -m "coisas"

Exemplo de mensagem melhor

git commit -m "Adiciona página de comentários"

Uma boa mensagem de commit deve explicar de forma simples o que foi alterado.

Arquivos que não devem ir para o GitHub

Nem todos os arquivos do projeto devem ser enviados para o GitHub. Alguns arquivos são locais, pesados ou contêm informações sensíveis.

Para controlar isso, usamos um arquivo chamado .gitignore. Ele informa ao Git quais arquivos e pastas devem ser ignorados.

Exemplo de .gitignore

.env
.venv/
venv/
__pycache__/
*.pyc
node_modules/
.vscode/

O arquivo .env, por exemplo, pode conter senhas, chaves secretas e URLs de banco de dados. Por isso, ele não deve ser enviado para um repositório público.

Controle de versão em equipe

Em equipes profissionais, o controle de versão é ainda mais importante. Várias pessoas podem trabalhar no mesmo projeto ao mesmo tempo, cada uma em uma funcionalidade diferente.

Um fluxo comum de equipe funciona assim:

Atualizar a main Criar uma branch Desenvolver a tarefa Fazer commits Enviar para o GitHub Abrir Pull Request Revisar o código Fazer merge

Esse fluxo evita que várias pessoas alterem diretamente a branch principal, diminuindo o risco de quebrar o projeto.

Pull Request

Pull Request é uma solicitação para juntar o código de uma branch com outra. Ele é muito usado no GitHub para revisar alterações antes que elas entrem na branch principal.

Em um Pull Request, outros desenvolvedores podem comentar, sugerir mudanças, aprovar ou solicitar correções no código.

Isso melhora a qualidade do projeto e ajuda a equipe a manter um padrão de desenvolvimento.

Dúvidas comuns

Preciso usar Git em projeto pequeno?

Sim. Mesmo em projetos pequenos, Git ajuda a manter o histórico organizado e permite voltar atrás caso alguma alteração quebre o código.

GitHub é obrigatório para usar Git?

Não. Git funciona localmente no seu computador. O GitHub é usado quando você quer armazenar o projeto online ou colaborar com outras pessoas.

Commit é a mesma coisa que salvar o arquivo?

Não. Salvar o arquivo apenas grava a alteração no computador. Commit registra aquela alteração no histórico do Git.

Posso apagar uma branch?

Sim. Depois que uma branch já foi integrada à branch principal, ela pode ser apagada para manter o repositório organizado.

O que acontece se eu errar um commit?

Existem formas de corrigir commits, reverter alterações ou criar novos commits corrigindo o problema. O importante é entender que o Git foi criado justamente para ajudar a lidar com mudanças.

Resumo profissional

Controle de versão é uma das bases do desenvolvimento moderno. Ele permite que projetos cresçam com organização, segurança e colaboração. Git é a ferramenta mais usada para esse controle, enquanto GitHub é uma das plataformas mais populares para hospedar e colaborar em projetos.

Aprender controle de versão é essencial para qualquer pessoa que deseja trabalhar com programação, desenvolvimento web, engenharia de software, análise de dados, inteligência artificial ou qualquer área que envolva criação e manutenção de código.
